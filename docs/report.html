结论先行

结论一

瓶颈不在"抖动"，而在"故障的发现与恢复"

丢包 5%、成串丢包、重复 5%，可用率全部维持 100%，50 Hz 通道的到达间隔抖动始终是 1 ms——因为通道够密（20 ms 一条），丢单条几乎不改变间隔分布。

真正的失效集中在两处，而且都不是抖动：一次 TCP 闪断让客户端段错误崩溃；一次 25 秒链路假死客户端全程无感。一句话——它扛得住"信号差"，扛不住"信号断"。

结论二

两处失效均已定位、修复、实测验证

闪断从"必崩"到"不崩"且恢复快 4.8 倍；假死从"测不到"到 4 秒内察觉。健康链路三项复测无退化。

结论三

只动 6 个文件、237 行，未改架构

全部落在 upstream/src/network/，不涉及协议、数据流、UI 或构建方式。

测试环境与性能参数

为什么不用真车也能测

客户端只依赖"3333 端口上有一个会说 MQTT 3.1.1、会发那 25 个 topic 的 broker"。它不关心谁在背后产生数据——裁判系统栈、官方选手端、电控主控，对它都只是"数据来源"，而这个来源可以在 MQTT 层被完整仿造。因此本预研不需要真车主控、不需要官方选手端、不需要裁判系统栈。

测量可信度：我修掉了自己三个测量缺陷

必须先说清楚，否则读者会拿到错的数字。

  • 订阅竞态假象：窗口起点取"首包时刻"，而客户端是逐个 topic 订阅的，订阅生效前的发送被算成"丢失"，健康链路上凭空造出 0.271% 假丢包。
  • 口径错误（最严重）：一度只统计"发出去之后又丢的"，把注入丢弃的排除在分母外——注入 5% 却报 0.8%，等于把故障藏起来。
  • 仪器失效被误读成数据丢失：崩溃场景下日志中途死亡，分析器把之后所有投递记为"丢失"，得出 19% 的假丢包。

从基线里读出的三件事

低速率通道是短板，且差两个数量级。同一条链路、同一次 5% 丢包：

topic速率抖动 J
CustomByteBlock50 Hz1 ms

RobotModuleStatus1 Hz989 ms
 1 Hz 通道丢一条，间隔就从 1000 ms 变 2000 ms。血量、经济、模块灯、比赛阶段全在这类通道上。

抖动比丢包危险。注入 60±40 ms 抖动时链路一条没丢（0.14%），但乱序率 31.7%，有效更新率从 49.8 Hz 掉到 34.02 Hz。

最致命的两个问题与丢包无关。闪断后客户端重连成功、重新订阅成功，但上行发送永久停止、日志死亡，20 秒后段错误。假死 25 秒客户端一次都没发现——MQTT 规定"keepalive 内发过任何包就不必发 PINGREQ"，而客户端持续以约 2 Hz 上行发包，永远不触发 PINGRESP 超时，20 秒心跳根本没有生效的机会。

崩溃的根因（ASan 定位）

没有调试器，我用 AddressSanitizer 重建了一份客户端（构建参数走命令行，不改任何文件），拿到精确调用栈：

WARN QObject::startTimer: Timers can only be used with threads started with QThread
AddressSanitizer: SEGV in QTimer::start()
  #1 MqttLogger::startSession()    MqttLogger.cpp:86
  #8 MqttManager::connectionStateChanged
  #9 MqttManager::onConnectCompleted

MqttLogger 单例里的 QTimer 负责定时刷盘，而它的线程归属由"谁第一个调用 instance()"决定。诊断输出坐实：它创建在 Paho 回调线程上（不是 QThread）。logRx() 跑在那个线程，于是这个定时器既 start 不了也 stop 不掉——第一次连接只留一条警告，第一次掉线重连时直接段错误。

中途我曾用 moveToThread() 把宿主搬到主线程，警告消失了，但崩溃点转移到了 QTimer::timerEvent()——跨线程搬 QTimer 本身就不被 Qt 支持。最终改为彻底移除该定时器。

三处改动

#改动说明
1移除 MqttLogger 的 QTimer改为缓冲满就地刷盘。同样批量写，但不再依赖 Qt 定时器，也就无所谓线程归属
2重连：固定 5 s ＋ 3 次上限 → 指数退避＋抖动、上限 2 s、不限次数原策略每掉一次线白等 5 秒；broker 中断超约 26 秒后永久放弃重连，只能人工干预
3新增业务层数据存活看门狗数据静默超 3 秒 → 判假死、发信号、强制重建连接。这是 MQTT 层永远做不到的事

退避上限为什么是 2 秒：看门狗会主动拆连接，而链路中断期间连不回来；等链路恢复时，客户端最坏要等"下一次重试"才连得上——这个等待直接算进恢复延迟。上限越大恢复越慢，越小重试越密。2 秒是权衡点：最坏多等约 2 秒，重试频率仅 0.5 次/秒（20 台同时重连也只是 10 次/秒）。

关于"假死中断总时长反而多了 1.1 秒"，必须如实说明：基线不拆连接，黑洞一结束数据立刻恢复（恰好 25 s）；看门狗拆了连接，链路恢复后要等下一次重试才连上（+1.1 s）。用 1.1 秒的恢复延迟，换来"4 秒内察觉 ＋ 保证最终恢复"——如果黑洞持续下去，基线是永久瞎，看门狗会一直重试直到链路回来。

未提升的两项，以及为什么

退回基线 低频通道抗抖动差——客户端侧无解。1 Hz 通道丢一条间隔就翻倍。这个抖动不是客户端造成的，也不在客户端能修的范围内：数据根本没到。任何平滑、插值、预测都只是把"没有数据"伪装成"有数据"，对操作手是危险的。真正的解法在上游。

退回基线 延迟抖动下的 31.7% 乱序丢弃——复查后判定不是缺陷。规则是"丢弃乱序旧包"，对连续量而言这是正确的：序号 1,3,2,5,4 到达时被丢的是 2 和 4，留下来的永远是最新的值。数据从不陈旧，只是采样率从 50 Hz 降到 34 Hz——人眼不可分辨。任何"保留旧包"的改动都会让显示变旧，是负优化。

仍然存在的空白

  • 看门狗尚未接到 UI：mqttDataStalled 信号已发出，但界面还没做"失联灰显"，操作手目前只能从日志知道。
  • 假死阈值 3 秒是拍的：需确认真实赛场最低频 topic 的周期后再定；已支持 RM_LIVENESS_TIMEOUT_MS 覆盖。
  • 真链路未验证：本次全部在 localhost 完成。图传无线链路的成串丢包特征、官方选手端 broker 的真实行为都仿不出来，需现场复测。

开源技术与概念

概念：抖动分三种形态，吃三种药

形态表现药
丢少了一段数据序号＋只认最新（连续量）；重传＋ack（离散量）
重 / 乱同一段来两次、顺序颠倒序号去重，只接受更新的包
晚 / 假死连接还在，数据停了心跳＋业务层新鲜度判定＋超时降级

本项目的关键教训：第三种形态用前两种的药治不好。心跳与 QoS 重传在"连接还活着但对端不说话"时全部失效。

概念：为什么 MQTT 心跳救不了假死

MQTT 3.1.1 规定客户端只要在 keepalive 周期内发过任何一个包，就不必发 PINGREQ；而 Paho 的失联判定只发生在 PINGRESP 超时时。于是出现一个反直觉的结论：客户端越"勤快"（持续上行），越发现不了下行断路。

这正是工业界标准做法——ROS 2 QoS 的 deadline ＋ liveliness——存在的原因：传输层心跳只管"连接死没死"，业务层必须自己声明"我至少每 X ms 该收到一次数据"。我们的 3 秒看门狗就是这套模型的最小实现。

概念：指数退避与抖动

固定间隔重连在多客户端场景会形成重连风暴：20 台同时掉线又同时重连，把 broker 打崩。标准解法是 Exponential Backoff ＋ Jitter（Marc Brooker / AWS Well-Architected REL05-BP03）。我们采用带下限的抖动：

exp   = min(base × 2ⁿ, cap)     // 500, 1000, 2000（封顶）
delay = random(exp/2, exp)      // 抖动区间

取 [exp/2, exp] 而非教科书里的 [0, exp]（full jitter），是因为 full jitter 会退避到接近 0 变成忙等；带下限既打散多机重连时刻，又保留合理的最小等待。

一个方法论收获

真正打通问题的不是某个开源库，而是三件事的组合：

  • 自己写故障注入器——只有掌握投递时刻的一方才能注入"消息级"故障。字节级工具做不到。
  • sha1 精确配对——不靠时间戳猜"哪条丢了"，而是让收发两端按消息指纹相认。所有指标因此是确定的，不是统计推测。
  • 不依赖被测对象的探针——日志会在崩溃时失效，但"它还在不在发包"骗不了人。正是这一条把"半死"定性成了"崩溃"。

如果只允许留一条经验：测量系统本身必须先被验证。本次修掉的三个测量缺陷里，有两个如果不修，会分别得出"健康链路丢 0.27%"和"注入 5% 却只丢 0.8%"两个错误结论——而它们看起来都很合理。
