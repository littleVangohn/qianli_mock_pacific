# 抗抖动能力评估与测试

对象：本客户端（C++/Qt）的 **MQTT 数据层**，即 `MqttManager` + `NetworkManager` + `GameData`。

本文回答五件事：**现在差在哪、用什么数衡量、怎么测出来、怎么改（不换架构）、有哪些开源能借**。

"抖动"在这里拆成三种形态，**不同形态吃不同的药**：

| 形态 | 表现 | 药 |
|---|---|---|
| 丢 | 少了一段数据 | 序号 + 只认最新（连续量）/ 重传 + ack（离散量） |
| 重 / 乱 | 同一段来两次、顺序颠倒 | 序号去重，只接受更新的包 |
| 晚 / 假死 | 连接还在，数据停了 | 心跳 + 新鲜度判定 + 超时降级 |

---

## 1. 现状：三个真硬伤

### 1.1 断线约 26 秒后，永久放弃重连 ★最严重

`onConnectCompleted()` 里 `m_retryCount` 上限为 3，第四次尝试失败后打出
`Max retry attempts reached, giving up` 并**不再重启定时器**
（[MqttManager.cpp:477-483](../upstream/src/network/MqttManager.cpp#L477-L483)）。

时间线（`connectTimeout = 2`、固定间隔 5 s）：

```
t=0    连接丢失 → 启动重连定时器
t=5    第 1 次尝试 → 失败 → m_retryCount=1
t=12   第 2 次尝试 → 失败 → m_retryCount=2
t=19   第 3 次尝试 → 失败 → m_retryCount=3
t=26   第 4 次尝试 → 失败 → 计数已满 → 放弃，且不再重启定时器
```

**broker 中断超过约 26 秒，客户端就再也回不来**，只能手动切换机器人或重启客户端。
比赛中官方选手端重启、网络闪断都足以触发。

而且没有兜底：`MainWindow` 那套带 ClientId 轮换的重连调度
（`scheduleMqttReconnect`）**只在启动/切换路径上被调用**——
`NetworkManager::errorOccurred` 全仓没有任何消费者
（[NetworkManager.cpp:1073-1074](../upstream/src/network/NetworkManager.cpp#L1073-L1074) 只是信号转发），
且判定函数 `shouldScheduleMqttRetry` 的关键词表
（[MainWindowStatePolicy.h:18-29](../upstream/src/ui/MainWindowStatePolicy.h#L18-L29)）
也认不出 `Connection lost` 这个字符串。

> 结论：**会话中途断线只有 MqttManager 这一条恢复路径，而它是有终点的。**

### 1.2 固定 5 秒重连，无退避、无抖动

`m_reconnectInterval = 5000` 是常量
（[MqttManager.cpp:162](../upstream/src/network/MqttManager.cpp#L162)）。
多台客户端同时掉线会**同时**重连，形成同步脉冲打向同一个 broker
（本场景里 broker 就是官方选手端，承受力有限）。重连时刻的标准差 ≈ 0，
是重连风暴最坏的形态。

### 1.3 假死要 20~40 秒才发现，而业务层只兜住了 1/25 个数据源

- 传输层：`keepAliveInterval = 20`
  （[MqttManager.cpp:94](../upstream/src/network/MqttManager.cpp#L94)）。
  MQTT 3.1.1 下 broker 侧在 1.5×keepAlive = 30 s 判死，客户端侧实测区间 20~40 s。
- 业务层：只有 `CustomByteBlock` 有新鲜度判定（300 ms），
  且 `GameData::myRobotCustomDataAgeMs()`
  （[GameData.cpp:4881](../upstream/src/core/GameData.cpp#L4881)）
  **全仓无调用者**——QML 没接，"能查"但**不生效**，UI 既不灰显也不降级。
- `DataFreshnessGuard`（四档 300/800/1500 ms，
  [DataFreshnessGuard.h:54-56](../upstream/src/core/DataFreshnessGuard.h#L54-L56)）
  只被战术分析器用在 `enemy_pos_*` 上，与主 HUD 的 25 个 topic 无关。

### 1.4 顺带的观测层缺陷（影响量化本身）

| 缺陷 | 位置 | 后果 |
|---|---|---|
| timeline 排序键提取只认 `mono_ms=` / `wall_ms=`，而 MQTT 事件用的是 `received_ms=` | [main.cpp:121-135](../upstream/src/main.cpp#L121-L135) | 落入兜底分支 `mono_ms=0\|`，**timeline.log 里所有 MQTT 事件排序键都是 0，时间线全乱**；只有 `RM26_VIDEO_*` 是对的 |
| `messageObserved` 的唯一消费者在 `RM26_ENABLE_DEVTOOLS` 里，该开关默认 OFF 且 `test/build.sh` 没开 | [MqttManager.h:128](../upstream/src/network/MqttManager.h#L128) | 普通构建下这个信号被直接丢弃 |
| DevHooks 的 trace 是 200 条内存环形缓冲，不落文件 | `ClientDevHooks.cpp:147-158` | 只能看最近 200 条，无法做长稳统计 |
| `seq` 丢弃点不计数 | [NetworkManager.cpp:1748-1753](../upstream/src/network/NetworkManager.cpp#L1748-L1753) | 丢包率/重复率/乱序率**当前不可观测** |

### 1.5 已经做对的（不要动）

| 项 | 位置 |
|---|---|
| `seq` 去重 + 乱序旧包丢弃 + 255 回绕判定 | [NetworkManager.cpp:1745-1757](../upstream/src/network/NetworkManager.cpp#L1745-L1757) |
| 重复包/旧包**不刷新**接收时间（避免掩盖故障） | 同上，`noteRobotCustomDataReceived` 只在通过校验后调用 |
| 按魔数 `0x5A` 分流状态包与视频分片，不再靠长度猜 | `CustomDataTypes.h` |
| `MqttLogger` 回调线程只入内存缓冲，刷盘交给定时器 | `MqttLogger.cpp:159-188` |

> `cleansession=1` **不应改**。对连续量补发积压数据是错的药——重连后会灌一堆过期值。
> "只认最新值"才是对的，这一点设计上没问题，写进文档让电控遵守即可。

## 2. 量化：用哪些参数

抗抖动能力 = 链路劣化时**维持数据可用**的能力。拆成四族，共 10 个可测参数。

| 参数 | 定义 / 公式 | 今天能否采到 | 当前基线 | 建议目标 |
|---|---|---|---|---|
| **A_max** 自愈上限 | 断线后仍能自动恢复的最长时长 | ✅ 可由代码推导 | **≈26 s** | 不限次 / ≥10 min |
| **T_recover** 恢复时延 | 链路恢复 → 数据重新可信 | ✅ | 均值 2.5 s / 最坏 5 s + 建连 + 订阅 | p95 ≤ 1.5 s |
| **T_dead** 假死检测 | 链路静默 → 判定断线 | ⚠️ 需实测 | 20~40 s | ≤ 10 s |
| **T_stale** 陈旧检测 | 数据停发 → 判不可信 | ⚠️ 有 API 未接线 | 300 ms | 接线并生效 |
| **C_guard** 新鲜度覆盖率 | 有超时判定的数据源 / 全部数据源 | ❌ | 1/25 | ≥ 8 个关键源 |
| **σ_reconnect** 风暴离散度 | 多实例重连时刻的标准差 | ✅ | ≈0 | ≥ 1 s |
| **L** 丢包率 | 缺失 seq / 期望 seq | ⚠️ 需补计数 | 未测 | < 1% |
| **D** 重复率 | `delta==0` 次数 / 总包数 | ⚠️ 需补计数 | 未测 | 记录（已丢弃） |
| **O** 乱序率 | `delta>127` 次数 / 总包数 | ⚠️ 需补计数 | 未测 | 记录（已丢弃） |
| **J** 到达间隔抖动 | p95(IPI) − p50(IPI) | ✅ 由 `RM26_MQTT_RX_TIMING` 算 | 未测（局域网应 < 5 ms） | < 10 ms |
| **Q** UI 排队延迟 | 处理时刻 − `received_ms` | ⚠️ 需补一处打点 | 未测 | p99 ≤ 20 ms |
| **A** 数据可用率 | Σ可信时长 / 总时长 | ✅ 采样 ageMs | 未测 | ≥ 99% / 30 min |

**对外只需要四个数**：`A_max`、`T_recover`、`T_dead`、`A`。其余是定位问题用的。

### 采集管线（已经现成，缺的只是聚合）

客户端日志由 `main.cpp:90-143` 的运行时处理器落盘：

```
<启动目录>/tmp/runtime_<时间戳>/runtime.log     # 全量
<启动目录>/tmp/runtime_<时间戳>/timeline.log    # 只含 MQTT 与图传关键事件
```

（`test/run.sh` 会 `cd ~/rm26-build` 再启动，所以实际在 `~/rm26-build/tmp/runtime_*/`。
可用环境变量 `RM_RUNTIME_LOG_PATH` 改。）

原始素材：

```
RM26_MQTT_RX_TIMING direction=rx topic=<名字> received_ms=<毫秒> bytes=<大小> sha1=<sha1>
```

- `received_ms` → 算 `J`（到达间隔分布）、`Q`
- `sha1` → 算 `D`（重复检测），不需要改代码
- `seq` → 算 `L` / `O`，**需要先补计数**

> 注意两点：① 高频视频（`CustomByteBlock` 且 >100 字节）默认**每秒只采样一条**，
> 要逐条需设 `RM_VERBOSE_VIDEO_LOG=1`；11 字节的状态包不受此限。
> ② `runtime.log` 每 64 行才 flush 一次，**别用 `kill -9` 收尾**，否则丢尾部数据。

## 3. 怎么测出来

### 3.1 注入手段

前提：`RM_MQTT_BROKER` / `RM_MQTT_PORT` 支持环境变量覆盖
（[ConfigManager.cpp:120-125](../upstream/src/config/ConfigManager.cpp#L120-L125)），
所以挂故障注入代理**不用改 config.json**：

```bash
RM_MQTT_PORT=3334 bash run.sh
```

| 抖动形态 | 注入手段 | 得到哪个参数 |
|---|---|---|
| 断连 | toxiproxy `reset_peer`；或直接杀 broker | `A_max`、`T_recover` |
| **假死**（连接在、数据停） | toxiproxy **`timeout` toxic**（最干净）；或 `iptables -A OUTPUT -p tcp --dport 3333 -j DROP` | `T_dead` |
| 延迟 / 抖动 | toxiproxy `latency` | `J`、`Q` |
| 丢包 / 重复 / 乱序 | `tc netem loss N% duplicate N% reorder N%` | `L`、`D`、`O` |
| 应用层停发 | 停 `upstream/sim/` 的 publisher | `T_stale`、`A` |
| 高频灌包（背压） | 另开一个 ClientId 按 50~500 Hz 发 `CustomByteBlock` | `Q` |
| 重连风暴 | 同时起 N 个客户端实例，同时断 | `σ_reconnect` |

两个注意：

- **`tc netem` 在 WSL 里未必可用**（内核可能没编 `sch_netem`）。
  先验证 `sudo tc qdisc add dev eth0 root netem delay 1ms`，失败就改用 toxiproxy——
  它是用户态代理，不依赖内核模块，Windows 侧也能跑。
- 灌包脚本可基于 `upstream/sim/server/industrial_camera_streamer.py`
  改（它本来就在往 `CustomByteBlock` 推 H.264 分片）。
  `upstream/sim/` 是**种子驱动**的（`DEFAULT_SEED = 2026`），实验可复现。

### 3.2 流程

1. 开注入代理，记录每次故障的起止墙钟时刻；
2. 跑 `run.sh` 采集 `runtime.log`；
3. 用 `RM26_MQTT_RX_TIMING` 的 `received_ms` 与故障时刻对齐 → 得 `T_dead` / `T_recover` / `A_max`；
4. 统计到达间隔与 `sha1` → 得 `J` / `D`；
5. 补了 seq 计数后 → 得 `L` / `O`。

## 4. 怎么优化（不换架构）

全部落在既有文件里，约 40 行。

| 改动 | 位置 | 规模 |
|---|---|---|
| 去掉 3 次上限 → 不限次重连 | [MqttManager.cpp:477-483](../upstream/src/network/MqttManager.cpp#L477-L483) | ~5 行 |
| 重连改指数退避 + full jitter，上限 2~5 s | [MqttManager.cpp:162](../upstream/src/network/MqttManager.cpp#L162) + `tryReconnect` | ~15 行 |
| `keepAlive` 20 → 8~10 s | [MqttManager.cpp:94](../upstream/src/network/MqttManager.cpp#L94) | 1 行 |
| `NetworkManager::errorOccurred` 接到 `scheduleMqttReconnect`，关键词补 `connection lost` | MainWindow 构造 + [MainWindowStatePolicy.h:18](../upstream/src/ui/MainWindowStatePolicy.h#L18) | ~6 行 |
| seq 丢弃点补计数（重复 / 乱序 / 缺口） | [NetworkManager.cpp:1748-1753](../upstream/src/network/NetworkManager.cpp#L1748-L1753) | ~8 行 |
| 处理时刻打点（算 `Q`） | `NetworkManager::processMqttMessage` | ~4 行 |
| 把 `myRobotCustomDataAgeMs()` 接到界面做灰显 | QML 各面板 | ~10 行 |
| 修 timeline 排序键：`received_ms=` 也纳入提取 | [main.cpp:121-135](../upstream/src/main.cpp#L121-L135) | ~3 行 |

退避公式用 AWS 的 **full jitter**：

```
sleep = random(0, min(cap, base * 2^n))
```

`base = 0.5 s`、`cap = 5 s`，n 为连续失败次数。既避免同步脉冲，
又不会像纯指数退避那样在长时间故障后迟迟不重试。

**`keepAlive` 的取舍**：调小能更快发现假死，但链路上行会被 PINGREQ 占用一点带宽，
且拥塞时容易误判。8~10 s 是平衡点。

## 5. 开源可借鉴

| 工具 / 资料 | 用途 | 说明 |
|---|---|---|
| **toxiproxy**（Shopify） | 网络故障注入：`latency` / `timeout` / `reset_peer` / `slicer` / `limit_data` | MIT，Go，有 Windows 二进制，**不依赖内核模块——首选** |
| `tc netem` | 内核级丢包 / 延迟 / 乱序 / 重复 / 损坏 | Linux 自带，脚本化最方便 |
| **mochi-mqtt/server** | Go MQTT broker | 本地 `_oss_reference/RMMock` 已用它起了 `:3333`，改几行就是**可编程的故障 broker** |
| RMMock | 官方客户端替身（broker + 假数据），可脱离赛事引擎开发 | `_oss_reference/RMMock` |
| SharkClient（Rust + rumqttc） | 另一套自定义客户端实现，可对照其重连参数 | `_oss_reference/SharkClient` |
| emqtt-bench / mqtt-benchmark | MQTT 压测（连接数 / 吞吐） | 用于测 broker 承受力与重连风暴 |
| Paho C `MQTTAsync.automaticReconnect` + `minRetryInterval`/`maxRetryInterval` | 指数退避重连的**参考实现** | 已确认存在于本机 1.3.9 的 `MQTTAsync.h:1303`；注意**仅异步 API**，本项目用的同步 `MQTTClient` 没有这个字段 |
| paho.mqtt.testing | Eclipse 官方互操作 / 一致性测试套件 | EPL |
| ROS 2 QoS `deadline` / `liveliness` | 业务层新鲜度判定的设计参照 | 与我们"300 ms 超时 + 变灰"是同一模型 |
| AWS *Exponential Backoff And Jitter* | full jitter 公式与三种抖动策略 | 见第 4 节 |
| EMQX 会话与消息过期 / HiveMQ MQTT Essentials | `cleansession`、retained、LWT 的语义 | 决定"断线窗口丢包"行为的依据 |

## 6. 一句话总结

链路层（去重、乱序、魔数分流、日志缓冲）**已经做得不错**；
缺的是**恢复的韧性**（26 秒后永久放弃）与**可观测性**（丢包/重连/排队都无计数）。
前者约 20 行代码，后者约 15 行——都不需要动架构。
