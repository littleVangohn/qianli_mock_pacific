## 一、结论先行

### 结论 1：原系统的瓶颈不在"抖动"，而在"故障的发现与恢复"

这是本次预研最反直觉的发现。我们原本以为丢包和延迟是主要威胁，实测结果相反：

- **链路劣化基本打不垮它**。丢包 5%、成串丢包、重复 5%，可用率全部维持 **100%**，50Hz 通道的到达间隔抖动始终是 **1 ms**。原因是通道足够密（20ms 一条），丢单条几乎不改变间隔分布。
- **真正的失效集中在两处**，而且都不是"抖动"：
  - 一次 TCP 闪断（RST）→ 客户端 **段错误崩溃**，上行发送与日志永久失效
  - 一次 25 秒的链路假死 → 客户端 **全程无感**，既不报警也不重连

换句话说：**它扛得住"信号差"，扛不住"信号断"。**

### 结论 2：两处失效均已定位、修复并实测验证

| 指标 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| TCP 闪断后客户端状态 | **段错误崩溃**（上行与日志永久失效） | 正常恢复，无崩溃 | 从"必崩"到"不崩" |
| 闪断恢复时延 | 5.30 s | **1.10 s** | **4.8 倍** |
| 闪断场景可用率 | 92.3% | **96.0%** | +3.7pt |
| 假死检测时延 | **永不**（>25 s 完全无感） | **4.03 s** | 从"测不到"到"4 秒" |
| 链路恢复后回归时延 | 无（若中断持续则永不恢复） | **0.93 s** | 新增能力 |
| 健康链路表现 | 抖动 1 ms / 可用率 100% | 无退化（3/3 次复测 100%） | — |

### 结论 3：修复只动了 6 个文件、237 行，未改架构

全部落在 `upstream/src/network/` 下，不涉及协议、数据流、UI 或构建方式：

| 文件 | 改动行数 | 改了什么 |
|---|---|---|
| `MqttLogger.h` / `.cpp` | 11 / 67 | 移除线程归属错误的 `QTimer`，改为缓冲满就地刷盘 |
| `MqttManager.h` / `.cpp` | 19 / 66 | 重连改指数退避+抖动、取消"3 次后放弃"、`keepAlive` 20→10s、新增 `forceReconnect()` |
| `NetworkManager.h` / `.cpp` | 23 / 51 | 新增业务层"数据存活看门狗" |

## 二、测试环境与性能参数

### 2.1 为什么不用真车也能测

关键认识：**客户端只依赖"3333 端口上有一个会说 MQTT 3.1.1、会发那 25 个 topic 的 broker"**。它不关心谁在背后产生数据——裁判系统栈、官方选手端、电控主控，对它而言都只是"数据来源"，而这个来源可以在 MQTT 层被完整仿造。

因此本预研的测试环境**不需要真车主控、不需要官方选手端、不需要裁判系统栈**。

### 2.2 环境构成

```
┌─ WSL ──────────────────────────────────────────────────────┐
│                                                            │
│   mock_broker.py ──┬── MQTT broker (自己实现)               │
│   (单一进程三个角色) ├── 数据源：CustomByteBlock 50Hz         │
│                    │        + 5 个比赛 topic (1~5Hz)        │
│                    └── 故障注入器 + 基准记录器                │
│                              │                             │
│                              ▼ MQTT (TCP)                  │
│                     RoboMasterClient2025  ← 被测对象         │
│                              │                             │
│                              ▼                             │

│                              │                             │
```

### 2.3 性能参数定义

| 参数 | 定义 | 为什么它是关键 |
|---|---|---|
| **端到端丢失率** | (本该投递 − 实际收到) / 本该投递 | 用户可见的丢包；注意分母必须含"注入了但没发的"，否则会把故障藏起来 |
| **到达间隔抖动 J** | p95(相邻到达间隔) − p50 | 抖动的主指标；对 50Hz 通道 p50≈20ms |
| **数据可用率 A** | 1 − Σ(超阈值空档) / 总时长，阈值 300ms | 直接对应"UI 会灰多久" |
| **最长数据中断** | 单个最大空档 | 比平均值重要得多——操作手只会记得最长的那次 |
| **T_recover 恢复时延** | 故障结束 → 数据重新可信 | 决定"抖一下要瞎多久" |
| **T_dead 假死检测时延** | 链路静默 → 客户端察觉 | 决定"瞎了知不知道" |
| **有效更新率** | 按客户端去重规则重放后，真正进入 GameData 的条数/秒 | 区分"收到了"与"用上了" |
| **重连次数** | broker 侧观测到的连接次数 − 1 | 判断是真恢复还是反复抽搐 |

指标全部由 `analyze.py` 自动算出，原始数据（发送记录、事件流、客户端日志）逐场景留档在 `test/jitter/out/<时间戳>-<场景>/`。

### 2.4 故障注入能力

| 故障类型 | 注入方式 | 模拟的真实场景 |
|---|---|---|
| 均匀丢包 | `--drop-rate P` | 链路误码 |
| **成串丢包** | `--burst-gb/--burst-bg`（两状态马尔可夫 / Gilbert-Elliott） | **无线链路的真实形态**——丢包是成串的，不是均匀的 |
| 延迟抖动 | `--delay-ms X --delay-jitter-ms Y` | 无线链路时延波动 |
| 重复投递 | `--dup-rate P` | QoS 1 的 at-least-once 语义 |
| **假死（黑洞）** | `--scenario blackhole@T+D` | **TCP 还连着，但对端不再应答**——包括握手包也丢弃 |
| 业务层停发 | `--scenario freeze@T+D` | 上游没数据了，但心跳正常 |
| 强制断连 | `--scenario reset@T` | 用 `SO_LINGER=0` 发**真 RST** |

同时提供**不依赖客户端日志的存活探针**：broker 侧统计客户端主动发来的包数，每 5 秒记一次快照。
这一条在定位崩溃时是决定性的——客户端日志会失效，但它还在不在发包骗不了人。

### 2.5 测量可信度：我修掉了自己三个测量缺陷

必须先说清楚，否则读者会拿到错的数字：

1. **订阅竞态假象**：统计窗口起点取"首包时刻"，而客户端是逐个 topic 订阅的，订阅生效前的发送被算成"丢失"，在健康链路上凭空造出 0.271% 假丢包。→ 改为按"该 topic 订阅生效时刻"取窗。
2. **口径错误（最严重）**：一度只统计"发出去之后又丢的"，把注入丢弃的那部分排除在分母外——**注入 5% 却报 0.8%**，等于把故障藏起来。→ 改为端到端可见丢失率。
3. **仪器失效被误读成数据丢失**：崩溃场景下客户端日志中途死亡，分析器把之后所有投递记为"丢失"，得出 19% 的假丢包。→ 引入存活探针交叉验证，并在报告中标注哪些数字不可用。

## 三、基线与现状对比

### 3.1 基线全景（改动前实测）

| 场景 | 注入 | 端到端丢失 | 乱序 | 可用率 | 最长中断 | 抖动 J |
|---|---|---|---|---|---|---|
| 健康 | 无 | 0% | 0% | 100% | 0.04 s | 1 ms |
| 丢包 1% | `drop 0.01` | 1.13% | — | 100% | 0.06 s | 1 ms |
| 丢包 5% | `drop 0.05` | 3.96% | — | 100% | 0.06 s | 1 ms |
| 成串丢包 | 马尔可夫 | 3.00% | — | 100% | 0.16 s | 1 ms |
| **延迟抖动** | 60±40 ms | 0.14% | **31.7%** | 100% | 0.09 s | **37 ms** |
| 重复 5% | `dup 0.05` | 0% | — | 100% | 0.06 s | 1 ms |
| 业务层停发 | freeze 10s | — | — | 82.5% | **10.02 s** | 1 ms |
| **假死 25s** | blackhole | — | — | 71.8% | **25.02 s** | 1 ms |

### 3.2 从基线里读出的三件事

**（1）低速率通道是短板，且差两个数量级。** 同一条链路、同一次 5% 丢包：

| topic | 速率 | 抖动 J |
|---|---|---|
| CustomByteBlock | 50 Hz | **1 ms** |
| GameStatus | 5 Hz | 199 ms |
| GlobalUnitStatus | 2 Hz | 500 ms |
| RobotModuleStatus | 1 Hz | **989 ms** |

原因很朴素：1Hz 通道丢一条，间隔就从 1000ms 变 2000ms。**血量、经济、模块灯、比赛阶段全在这类通道上。**

**（2）抖动比丢包危险。** 注入 60±40ms 抖动时，链路一条没丢（0.14%），但乱序率 31.7%，有效更新率从 49.8Hz 掉到 34.02Hz——因为客户端的 `seq` 去重会丢弃乱序旧包。

**（3）最致命的两个问题与丢包无关**，而是：
- **闪断后崩溃**：客户端重连成功、重新订阅成功，但上行发送永久停止、日志死亡，20 秒后段错误。
- **假死无感**：25 秒完全黑洞，客户端一次都没发现。机制是——MQTT 规定"keepalive 内发过任何包就不必发 PINGREQ"，而客户端持续以约 2Hz 上行发包，于是**永远不触发 PINGRESP 超时**，20 秒心跳根本没有生效的机会。

### 3.3 崩溃的根因（ASan 定位）

没有调试器，我用 AddressSanitizer 重建了一份客户端（构建参数走命令行，不改任何文件），拿到精确调用栈：

```
WARN QObject::startTimer: Timers can only be used with threads started with QThread
AddressSanitizer: SEGV in QTimer::start()
  #1 MqttLogger::startSession()    MqttLogger.cpp:86
  #8 MqttManager::connectionStateChanged
  #9 MqttManager::onConnectCompleted
```

**根因**：`MqttLogger` 单例里的 `QTimer` 负责定时刷盘，而它的线程归属由"谁第一个调用 `instance()`"决定。诊断输出坐实：

```
[diag] instance(): created on QThread(0x374010)   ← Paho 回调线程（不是 QThread）
                   now on     QThread(0x6150)     ← 主线程
```

`logRx()` 跑在 Paho 回调线程上，于是这个定时器既 start 不了也 stop 不掉。**第一次连接只留一条警告，第一次掉线重连时 `QTimer::start()` 直接段错误——客户端第一次掉线必崩。**

中途我曾用 `moveToThread()` 把宿主搬到主线程，警告消失了，但**崩溃点转移到了 `QTimer::timerEvent()`**——说明跨线程搬 `QTimer` 本身就不被 Qt 支持。最终改为**彻底移除该定时器**，用"缓冲区满就地刷盘"实现同样的批量写目的。

### 3.4 三处改动

| # | 改动 | 说明 |
|---|---|---|
| 1 | **移除 `MqttLogger` 的 `QTimer`** | 改为缓冲满就地刷盘。同样批量写，但不再依赖 Qt 定时器，也就无所谓线程归属 |
| 2 | **重连策略：固定 5s + 3 次上限 → 指数退避 + 抖动、上限 2s、不限次数** | 原策略有两个致命点：每掉一次线白等 5 秒；broker 中断超过约 26 秒后**永久放弃重连**，只能人工干预 |
| 3 | **新增业务层数据存活看门狗** | 连接正常但数据静默超过 3 秒 → 判定假死、发出信号、强制重建连接。这是 MQTT 层永远做不到的事 |

附带：`keepAlive` 20s → 10s（让"连接真死"的发现时间从最长 30s 缩到 15s）。

**退避上限为什么是 2 秒**：看门狗会主动拆连接，而链路中断期间连不回来；等链路恢复时，客户端最坏要等"下一次重试"才连得上——**这个等待直接算进恢复延迟**。上限越大恢复越慢，上限越小重试越密。2 秒是权衡点：最坏多等约 2 秒，而重试频率仅 0.5 次/秒（20 台客户端同时重连也只是 10 次/秒，打不垮 broker）。

### 3.5 改动前后对比（实测）

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 闪断后客户端 | **SIGSEGV 崩溃** | 不崩（ASan 下 3/3 通过） |
| 闪断恢复时延 | 5.30 s | **1.10 s** |
| 闪断场景可用率 | 92.3% | **96.0%** |
| 假死检测时延 | 永不（>25 s 无感） | **4.03 s** |
| 假死中断总时长 | 25.02 s | 26.12 s |
| 链路恢复后回归 | 无 | **0.93 s** |
| 健康链路 | 100% / 抖动 1ms | **无退化**（3/3 次复测 100%） |

**关于"假死中断总时长反而多了 1.1 秒"**：这是看门狗的固有代价，必须如实说明。基线不拆连接，所以黑洞一结束数据立刻恢复（恰好 25s）；看门狗拆了连接，链路恢复后要等下一次重试才能连上（+1.1s）。**用 1.1 秒的恢复延迟，换来"4 秒内察觉 + 保证最终恢复"**——如果黑洞持续下去，基线是永久瞎，看门狗会一直重试直到链路回来。这笔交易在比赛场景下是划算的。

### 3.6 未提升的两项，以及为什么

**（1）低频通道抗抖动差 —— 客户端侧无解，退回基线。**
1Hz 通道丢一条，间隔就翻倍。这个抖动不是客户端造成的，也不在客户端能修的范围内——**数据根本没到**。任何平滑、插值、预测都只是把"没有数据"伪装成"有数据"，对操作手是危险的。真正的解法在上游（官方选手端对低频关键 topic 冗余重发或缩短发布周期），不在我们可控范围。

**（2）延迟抖动下的 31.7% 乱序丢弃 —— 复查后判定不是缺陷，退回基线。**
客户端的规则是"丢弃乱序旧包"。对连续量而言这**是正确的**：序号 1,3,2,5,4 到达时，被丢的是 2 和 4，留下来的永远是最新的值。数据**从不陈旧**，只是采样率从 50Hz 降到 34Hz——对姿态角、血量数字，34Hz 与 50Hz 人眼不可分辨。任何"保留旧包"的改动都会让显示变旧，是负优化。

### 3.7 仍然存在的空白

- **看门狗尚未接到 UI**：`mqttDataStalled` 信号已发出，但界面还没有做"失联灰显"。操作手目前只能从日志知道，看不到。
- **假死阈值 3 秒是拍的**：真实赛场的低频 topic 最低频率需要确认后再定；目前已支持 `RM_LIVENESS_TIMEOUT_MS` 环境变量覆盖。
- **真链路未验证**：本次全部在 localhost 上完成。图传无线链路（5.15–5.25GHz）的成串丢包特征、以及官方选手端 broker 的真实行为（上行限频、桥接节流）都仿不出来，需要在现场复测。

## 四、开源技术与概念

### 4.1 概念：抖动分三种形态，吃三种药

| 形态 | 表现 | 药 |
|---|---|---|
| **丢** | 少了一段数据 | 序号 + 只认最新（连续量）；重传 + ack（离散量） |
| **重 / 乱** | 同一段来两次、顺序颠倒 | 序号去重，只接受更新的包 |
| **晚 / 假死** | 连接还在，数据停了 | 心跳 + **业务层新鲜度判定** + 超时降级 |

本项目的关键教训是：**第三种形态用前两种的药治不好**。MQTT 的心跳、QoS 的重传，在"连接还活着但对端不说话"时全部失效。

### 4.2 概念：为什么 MQTT 心跳救不了假死

MQTT 3.1.1 规定：客户端只要在 keepalive 周期内**发过任何一个包**，就不必发 PINGREQ。而 Paho 的失联判定**只发生在 PINGRESP 超时时**。

于是出现一个反直觉的结论：**客户端越"勤快"（持续上行），越发现不了下行断路**。我们的客户端以约 2Hz 持续发包，结果 25 秒完全黑洞全程无感。

这正是工业界标准做法——**ROS 2 QoS 的 `deadline` + `liveliness`**——存在的原因：传输层心跳只管"连接死没死"，业务层必须自己声明"我至少每 X ms 该收到一次数据"。我们实现的 3 秒看门狗，就是这套模型的最小实现。

> 参考：ROS 2 QoS 官方文档 · EMQX 会话与消息过期 · HiveMQ MQTT Essentials

### 4.3 概念：指数退避与抖动

固定间隔重连在多客户端场景会形成**重连风暴**：20 台客户端同时掉线，又同时重连，把 broker 打崩，然后一起再重连。

标准解法是 **Exponential Backoff + Jitter**（Marc Brooker / AWS Well-Architected REL05-BP03）。我们采用的是**带下限的抖动**：

```
exp   = min(base × 2^n, cap)        // 500, 1000, 2000（封顶）
delay = random(exp/2, exp)          // 抖动区间
```

取 `[exp/2, exp]` 而不是教科书里的 `[0, exp]`（full jitter），是因为 full jitter 会退避到接近 0，变成忙等；带下限既打散了多机重连的时刻，又保留一个合理的最小等待。

### 4.4 开源工具盘点

| 工具 | 用途 | 我们的选择 |
|---|---|---|
| **toxiproxy**（Shopify, MIT） | 用户态网络故障注入：`latency`/`timeout`/`reset_peer`/`slicer` | 未采用。它是 TCP 层代理，按字节丢包会切坏 MQTT 帧，测出来是"协议错误"而非"消息丢失" |
| `tc netem` | 内核级丢包/延迟/乱序 | 未采用。同上，且本机 WSL 内核未必编了 `sch_netem` |
| **mochi-mqtt/server**（Go, MIT） | 可编程 MQTT broker | 参考其设计。我们自己写 broker 是因为**要控制"消息级"投递时刻**，这是字节级工具做不到的 |
| **paho.mqtt.testing**（Eclipse） | MQTT 互操作一致性套件 | 未采用（针对 broker 实现） |
| **emqtt-bench** | MQTT 压测 / 重连风暴 | 备选。本场景只有 20 台客户端，用不上 |
| **Paho C `MQTTAsync.automaticReconnect`** | 内置指数退避重连 | 未采用。**仅异步 API 有**，本项目用的同步 `MQTTClient` 没有此字段（已核实本机 1.3.9 头文件） |
| **AddressSanitizer** | 内存错误检测 | **实际采用**。无 gdb 环境下定位段错误的决定性工具 |
| **ROS 2 QoS `deadline`/`liveliness`** | 业务层新鲜度判定的设计参照 | 概念参照 |

### 4.5 一个方法论收获

本次预研真正打通问题的**不是某个开源库，而是三件事的组合**：

1. **自己写故障注入器**——只有掌握投递时刻的一方，才能注入"消息级"故障（丢哪一条、延迟多久、重复几次）。字节级工具（netem/toxiproxy）做不到。
2. **sha1 精确配对**——不靠时间戳猜"哪条丢了"，而是让发送端和接收端按消息指纹相认。所有丢包/重复/乱序指标因此是**确定的**，不是统计推测。
3. **不依赖被测对象的探针**——客户端日志会在崩溃时失效，但 broker 侧"它还在不在发包"骗不了人。正是这一条把"半死"定性成了"崩溃"。

**如果只允许留一条经验**：测量系统本身必须先被验证。本次修掉的三个测量缺陷里，有两个如果不修，会分别得出"健康链路丢 0.27%"和"注入 5% 却只丢 0.8%"两个错误结论——而它们看起来都很合理。
