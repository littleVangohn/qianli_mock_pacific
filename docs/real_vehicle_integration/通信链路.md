# 通信链路

本文回答三件事：

1. 比赛数据（比分、血量、经济、位置）是怎么到我们客户端的；
2. 自家电控的数据（云台姿态、底盘模式、机构状态）将来怎么到我们客户端；
3. 链路上哪里会"抖"，业界怎么抗，上游开源本来做了什么、我们还缺什么。

写给不要求网络背景的读者。**每条结论都标了出处**：代码用 `文件:行`，硬件参数用官方手册页码，官方客户端的行为用其二进制里的字符串（IL2CPP 元数据）。

| 数据面 | 物理路径 | 内容 |

## 1. 五个概念（看懂后面就够）

**broker（消息中转站）**：一个进程，所有消息都发给它，再由它转发给订阅者。发布者和订阅者互相不认识，只认 topic。这里的 broker 是**官方选手端自己**（它在 3333 端口跑一个 MQTT server）。

**publish / subscribe / topic**：发布者往 `RobotDynamicStatus` 发，订阅了 `RobotDynamicStatus` 的人就收到。topic 就是"频道名"，不是队列——**同一条消息会复制给所有订阅者**。

**QoS（服务质量）**：0=最多一次（可能丢）、1=至少一次（**可能重复**）、2=恰好一次（开销大）。我们全部用 QoS 1 —— 所以"按序号去重"是协议要求，不是洁癖。

**会话（clean session）与保留消息**：`cleansession=1` 意思是"每次连接都是全新建档"，broker 不为离线的你排队（我们客户端就是这么配的）。**retained（保留消息）** 是另一回事：broker 为每个 topic 记住最后一条，新订阅者立刻能收到——用来解决"重连后第一帧空白"。

**心跳与"假死"**：TCP 连接看起来还活着，但对端程序已经死了/网线被拔了，这叫假死。靠心跳（keepAlive）发现，**我们的心跳是 20 秒**——意味着假死最长 20~30 秒才被发现。

**protobuf**：一种二进制序列化格式。消息体不是 JSON 文本，而是紧凑的二进制；**不认识的新字段会被自动忽略**（向前兼容好），但整体不是合法 protobuf 时整包丢弃。

## 2. 链路 A：比赛数据（血量 / 经济 / 位置）

### 2.1 三跳

1. **赛事端**（RMServer + 引擎）产生数据；
2. **官方选手端**用私有协议（TCP/UDP）从赛事端取数，然后在本地 MQTT server 上按 topic 转发——它不产生数据，只是**协议翻译器 + broker**；
3. **我们**连上 3333 订阅 topic（[NetworkManager.cpp:1096-1132](../../upstream/src/network/NetworkManager.cpp#L1096-L1132)）。

**为什么非要绕官方选手端，不能直连赛事端？** 因为身份、图传链路、上行限频、机器人视角过滤都由官方选手端掌握。这是赛制设计：自定义客户端只能看到"本机视角"的数据（例如 `GlobalUnitStatus` 只给己方机器人血量列表 + 敌方基地，不给敌方逐机器人血量）。

### 2.3 身份：ClientId 就是"我是哪台机器人"

- ClientId = **选手端 ID**，由界面选择的机器人类型决定（`mqttClientIdForRobotType` → `robotIdFromSettingsType`，[MainWindow.cpp:1583-1585](../../upstream/src/ui/MainWindow.cpp#L1583-L1585)）。
- 编号规则（[config.example.json](../../upstream/config.example.json) 注释）：**红方 1–7，蓝方 101–107**；客户端用 `getMyRobotId() >= 100` 判断蓝方视角。
- **同一个 ClientId 同一时刻只能有一个连接**。所以：

| 现象 | 原因 |
|---|---|
| `CONNACK(2): Identifier rejected` | 该 ClientId 已被占用（别的客户端/残留进程/桥接） |
| 服务器显示"3 号在线"但你在操作 4 号 | 身份被回退到了 config 里的默认 ID |

上游为此做了两层保护：候选 ClientId 列表 + 连接失败逐个换（[MainWindow.cpp:1495-1521](../../upstream/src/ui/MainWindow.cpp#L1495-L1521)），以及 5 秒固定间隔的重连定时器。

### 2.4 连接参数（上游设定，我们未改）

| 参数 | 值 | 后果 |
|---|---|---|
| 协议版本 | MQTT 3.1.1 | 不支持 MQTT 5 的 session expiry |
| `keepAlive` | 20 s | **假死最长 20~30 s 才发现** |
| `cleansession` | 1 | 断线窗口内的消息**永久丢失**，broker 不排队 |
| `connectTimeout` | 2 s | 切换机器人时不卡 UI |
| 连接方式 | `QThreadPool` 异步 | 主线程不阻塞 |
| 重连 | 固定 5 s 定时器 | **没有指数退避、没有抖动** |
| 订阅 QoS | 全 1 | 至少一次 → **可能重复** |

出处：[MqttManager.cpp:93-98](../../upstream/src/network/MqttManager.cpp#L93-L98)、[MqttManager.h:162](../../upstream/src/network/MqttManager.h#L162)。

**代码长这样**（[MqttManager.cpp:92-125](../../upstream/src/network/MqttManager.cpp#L92-L125)）：

```cpp
// 配置连接选项
MQTTClient_connectOptions connOpts = MQTTClient_connectOptions_initializer;
connOpts.keepAliveInterval = 20; // 心跳间隔 20秒
connOpts.cleansession = 1;       // 每次连接清除会话
connOpts.connectTimeout = 2;     // 连接超时 2秒，避免 UI 在切换机器人时长时间卡顿
connOpts.MQTTVersion = MQTTVERSION_3_1_1;  // 使用 MQTT 3.1.1（大多数 broker 要求）

// 真正异步执行 MQTTClient_connect：后台线程执行 TCP 连接，
// 主线程通过 onConnectCompleted 接收结果，完全无阻塞。
QThreadPool::globalInstance()->start([this, connOpts]() mutable {
  int result = MQTTClient_connect(m_client, &connOpts);
  QMetaObject::invokeMethod(this, [this, result]() {
    onConnectCompleted(result);
  }, Qt::QueuedConnection);
});
```

三个设计点值得注意：

1. `cleansession = 1` 与 `keepAliveInterval = 20` 决定了"断线即丢包"和"假死 20 秒才发现"这两条硬性质，见 5 节第 5、3 行；
2. 连接动作扔进 `QThreadPool`，结果用 `QueuedConnection` 送回主线程——**整个网络层不允许阻塞 UI**，这是上游的基调；
3. `MQTTClient_connect` 在别的线程里跑，但 `this`（MqttManager）是主线程对象：只要对象还活着就安全，这正是它用 `invokeMethod` 而不是直接调用的原因。

**重连也是同一种写法**（[MqttManager.cpp:36-44](../../upstream/src/network/MqttManager.cpp#L36-L44)、[:370-383](../../upstream/src/network/MqttManager.cpp#L370-L383)）：

```cpp
MqttManager::MqttManager(QObject *parent) : QObject(parent) {
  m_client = nullptr;
  m_reconnectTimer = new QTimer(this);
  m_reconnectTimer->setInterval(m_reconnectInterval);   // m_reconnectInterval = 5000
  connect(m_reconnectTimer, &QTimer::timeout, this, &MqttManager::tryReconnect);
}
```

```cpp
// 连接丢失回调（Paho 线程里执行）
QMetaObject::invokeMethod(
    self,
    [self, reason]() {
      self->m_connected = false;
      emit self->connectionStateChanged(false);
      emit self->errorOccurred(QString("Connection lost: %1").arg(reason));
      // 通过 QObject 所在线程启动重连定时器，避免 Paho 回调线程直接碰 Qt timer
      self->m_reconnectTimer->start();
    },
    Qt::QueuedConnection);
```

注释里那句"避免 Paho 回调线程直接碰 Qt timer"是**跨线程使用 Qt 对象的经典约束**：Qt 的定时器、信号槽都归属创建它的线程，从别的线程直接操作会静默失效甚至崩溃。整套代码反复在用 `invokeMethod(..., Qt::QueuedConnection)` 这一个手法把执行权搬回主线程，记住这一条，后面所有回调都看得懂了。

### 2.5 消息在客户端内部怎么走（含一个隐藏的坑）

```
Paho 回调线程
  messageArrivedCallback        ← 视频类消息按 1Hz 采样算 SHA1，避免拖慢
  MqttLogger::logRx             ← 同步写文件 + payload hex 转储（默认开启）
  invokeMethod(QueuedConnection)
        ↓
UI 线程
  NetworkManager::processMqttMessage   ← 25 个 topic 的 if-else + protobuf 解析
        ↓
  GameData（Q_PROPERTY + 信号）→ QML
```

**② 消息到达：从 Paho 线程跳回主线程**（[MqttManager.cpp:342-354](../../upstream/src/network/MqttManager.cpp#L342-L354)）——这是整条链路最关键的一次"交接"：

```cpp

QMetaObject::invokeMethod(
    self,
    [self, topic, payload, payloadSha1, receivedMs, observeMessage]() {
      if (observeMessage) {
        emit self->messageObserved(topic, payload.size(), payloadSha1, receivedMs);

      emit self->messageReceived(topic, payload);   // → NetworkManager::processMqttMessage
```

把它和上一节的参数表对起来看：**payload 被完整拷贝进 lambda，排队进主线程事件队列**。所以"UI 卡住 → 消息积压 → 数据变晚"的机制就在这里，而不是在网络上。也正因为如此，`logRx` 那一行（同步落盘 + 把 payload 转成 hex 字符串）是全链路唯一在回调线程里做 I/O 的地方。

**坑：上游写了一套"33ms 合并消息"的保护（`m_pendingMessages` + QTimer，注释写明"避免 UI 线程被高频 MQTT 阻塞"），但它在 `MqttClient`（Qt MQTT）分支里，而 CMake 只定义了 `RM_HAS_MQTT`（Paho）——那条分支根本没编译**（[CMakeLists.txt:485](../../upstream/CMakeLists.txt#L485)，全仓库搜不到 `RM_HAS_QT_MQTT` 的定义）。所以现在是**逐包直灌 UI 线程，没有批量、没有背压**。UI 一卡，消息不丢但会越来越晚。

对照着看这两段，差别一目了然——**没编译的那版反而更稳**（[MqttClient.cpp:358-381](../../upstream/src/network/MqttClient.cpp#L358-L381)）：

```cpp
void MqttClient::onMessageReceived(const QByteArray &payload, const QMqttTopicName &topic) {
  MqttLogger::instance()->logRx(topic.name(), payload);
  // 批量处理：将消息缓存在待处理队列，由定时器统一触发处理
  // 避免每个 MQTT 消息都同步阻塞 UI 线程进行 Protobuf 解析
  m_pendingMessages.append({topic.name(), payload});
  if (!m_processTimer->isActive()) {
    m_processTimer->start();          // 33ms 后统一处理一批
  }
}

void MqttClient::processPendingMessages() {
  auto batch = std::move(m_pendingMessages);   // 一次取走当前全部
  m_pendingMessages.clear();
  for (const auto &[topic, payload] : batch) {
    handlePayload(topic, payload);
  }
  if (!m_pendingMessages.isEmpty()) {          // 处理期间又来新的，再排一轮
    m_processTimer->start();
  }
}
```

而实际编译进去的那条（Paho）是**收到就发信号，直接进主线程解析**。所以"要不要启用批量"是我们自己可以决定的（改构建定义即可），但**它只是把解析挪到批量里，并不能减少总解析量**——真正的成本大头是每条消息的 protobuf 解析和 GameData 更新，这一点两种写法一样。

## 3. 链路 B：自家电控数据（云台姿态 / 底盘模式 / 机构状态）

### 3.1 为什么不能走 MQTT

车端没有 MQTT 客户端：电控主控是一块单片机，对外有两路串口——**裁判系统串口**（接 MC02，115200）和**图传串口**（接 VT03/VT13 发射端 UART，921600）。自定义数据 0x0310 走的是后者，与 21 字节遥控/键鼠帧同一条 UART，**不经过裁判系统主控**。MQTT 那条路只存在于"操作手 PC 内部"，是 PC 上几个进程之间的事。所以车端数据必须借道图传链路。

### 3.2 链路

```
电控主控 STM32
  └─ 图传模块发射端 UART（921600，与 21B 遥控/键鼠帧同一路）
       │  UART cmd 0x0310「自定义数据包（机器人→自定义客户端）」
图传模块发射端 VT03/VT13
       │
图传无线链路（与视频同一条链路）
       │
图传接收端（USB-C）→ 官方选手端 RoboMasterClient.exe
       │   官方客户端把车端自定义块桥接进内嵌 MQTT server
       ▼
MQTT topic `CustomByteBlock` { bytes data }   ← protobuf 外壳，data = 电控发的原始字节
       │
我们的 NetworkManager::parseCustomByteBlock → GameData → QML
```

> 裁判系统主控模块 MC02 通过航空插头给发射端供电、设置机器人 ID 和完成图传对频，
> **不在 0x0310 的数据路径上**。0x0310 是图传 UART 协议的一部分（官方客户端
> `vt_monitor_ext` 把它与遥控/键鼠数据放在同一组）；300B × 50Hz = 15kB/s
> 也超过裁判系统串口 115200 的带宽。

### 3.3 证据（为什么可以确定是这条）

| 结论 | 证据 |
|---|---|
| `0x0310` 走图传发射端 UART，不经过裁判系统主控 | VT03&VT13 说明书：发射端 UART 921600，21 字节遥控帧每 14 ms；UART 口接机器人主控，接收端 USB-C 接官方选手端。图传开源报告 Part 0：0x0310 是“机器人→图传链路→操作手客户端”，payload 150/300 B，50 Hz，最大 15 kB/s。官方客户端 `vt_monitor_ext` 把 0x0310 与 `rc_data`/`rc_pc_key_mouse_data` 放在同一组计数器。 |
| 官方客户端把车端块桥接成 MQTT | 二进制里的 `RobotCustomByteBlockEvent`、`CustomClientThread::OnRobotCustomByteBlock`、`MQTT.Server\|MyMqttServer`、`PublishBytesMsg` |
| topic 名与载荷 | `CCP\|CustomByteBlock`；proto 定义 `message CustomByteBlock { bytes data = 1; }`（[robomaster.proto:544](../../upstream/src/network/proto/robomaster.proto#L544)） |
| 方向 = 机器人 → 客户端 | 图传开源报告 Part 0：0x0310 是“机器人发送给自定义客户端的数据”；0x0311 是反方向。 |
| 帧长 | 0x0310 单帧 payload 定长 150 B（初始协议）或 300 B（V1.3），频率上限 50 Hz；我们的 11 字节应用负载放在 payload 开头。是否前置 mode 字节、如何填充待联调实测，见第 8 节。 |

```cpp
struct RobotCustomStatus {
    uint8_t magic;                    // Byte 0    固定 0x5A，与同通道视频分片区分
    uint8_t version;                  // Byte 1    本版 = 1
    union { struct { uint8_t fric_enabled:1, rammer_enabled:1, fire_permitted:1,
                            auto_lob_active:1, electrical_fault:1, pose_valid:1,
                            pitch_valid:1, reserve1:1; } bits; uint8_t byte; } friction_status;  // Byte 2
    union { struct { uint8_t chassis_mode:3, chassis_warning:1, reserve2:4; } bits; uint8_t byte; } chassis_status;  // Byte 3
    int16_t  gimbal_chassis_angle;    // Byte 4-5  0.0001 rad
    int16_t  chassis_yaw;             // Byte 6-7  0.0001 rad
    int16_t  barrel_pitch;            // Byte 8-9  0.0001 rad
    uint8_t  seq;                     // Byte 10   包序号
};
static_assert(sizeof(RobotCustomStatus) == 11, "RobotCustomStatus size must be 11 bytes");
```

> `chassisMode === 2` 这个魔法数字来自结构体里"0=正常 1=跟随 2=小陀螺 3=保护"的注释；一旦电控改了编码，QML 这边不会报错，只会**显示错误的模式**——这就是"裸结构体没有版本号"的代价，也是我们建议加 magic/version 的原因。

**坑 1（已修）：长度启发式分流。** 上游原来靠长度猜类型（28–100 字节当状态块，其余全喂给 H.264 组帧器，[VideoReceiver.cpp:608](../../upstream/src/network/VideoReceiver.cpp#L608) 还会把**最后一个字节**当 packetId），短视频分片会被误判成状态包、状态包也会污染视频组帧。现在改为**按魔数分流**：首字节 `0x5A` 且长度够 → 状态包；其余 → 视频。长度变化、链路补齐都不再影响判别。

**坑 2（已修）：文档与解析器原本是两套布局。** 原文档定义 10 字节包（0.0001 rad 角度、独立 status_bits），上游解析器读的是 28 字节 `RobotCustomStatus`（0.1°、位域分散、带 18 字节保留），两者对不上。定稿为 **11 字节、零保留**：

- Byte 0 `0x5A` 魔数、Byte 1 版本；Byte 2/3 两个位域字节；Byte 4–9 三个角度（`int16`，`0.0001 rad`）；Byte 10 `seq`；
- 上游遗留的四个字段（`super_cap_energy/max`、`target_distance_dm`、`ballistic_compensation`）删除——电容改由裁判系统提供，另两个本车不用；
- 5 个状态位放进 Byte 2 原有的空闲 bit（`fire_permitted` / `auto_lob_active` / `electrical_fault` / `pose_valid` / `pitch_valid`）；
- 角度**线上保持弧度**，客户端解析时解算成角度（`rad → deg`），GameData 与 QML 里的角度字段仍然全是"度"，界面代码不用动；
- 结构体缩短**不需要改路由**：长度下限本来就写的是 `sizeof(RobotCustomStatus)`，只有 `static_assert` 跟着变。

客户端侧的增量改动**已落地**（2026-10-13）：结构体加 3 个字段与 5 个位名、解析函数加 `seq` 去重与角度解算、GameData 暴露新字段与 `myRobotCustomDataAgeMs()`。剩余的只有**界面接线**：把 `chassisYaw` / `barrelPitch` 画到姿态图和俯仰尺上，并用 `myRobotCustomDataAgeMs() > 300` 做失联灰显。

**坑 3（已修）**：README 里原有一句"当前客户端解析器仍要求 28 字节外壳，见电控文档兼容说明"——电控文档从来没有这一节，属悬空引用。文档 v2 重写后，该句已改为直接指向包定义所在章节。

### 3.5 判定"这包数据能不能用"

文档已定义三条，**代码还没实现**：

1. `seq` 去重（QoS 1 会重复投递，旧包不得覆盖新包）；
2. 连续 300 ms 无新 `seq` → 整包判为通信超时（UI 变灰，保留最后值）；
3. `pose_valid` / `pitch_valid` 表示**数据源**可信与否，与通信超时是两件事；可用 = 未超时 且 对应有效位=1。

这三条是唯一能在"MQTT 活着但车端死了"时发现问题的机制（MQTT 层要 20 s 才发现）。

我们**不用自定义包**发控制，而是发官方标准消息 `KeyboardMouseControl`（[robomaster.proto:456](../../upstream/src/network/proto/robomaster.proto#L456)）：

键位是官方固定的（图传手册第 8/17 页，与我们代码 [MainWindow.cpp:5281-5315](../../upstream/src/ui/MainWindow.cpp#L5281-L5315) 一致）：

`publish()` 的默认签名是 `publish(topic, payload, qos = 1, waitForCompletionMs = 1000)`（[MqttManager.h:99-100](../../upstream/src/network/MqttManager.h#L99-L100)）——**默认会等最多 1 秒确认，但键鼠这条路显式传了 `0`：不等确认直接返回**。加上 `cleansession = 1`（断线不排队），命令在链路抖动时是真的会静默消失的。这条"限频 + 不等 ACK"的组合，就是第 8.1 节要向电控确认回执机制的原因。

- **官方客户端有上行限频器**（二进制里的 `SetCoolTime`、`IsCommandRateLimited`、`m_cmdWindowStart/m_cmdWindowCount`、`maxPerSecond`）。发太快会被静默丢弃，具体阈值需要实测。
- 我们的发布**不等 ACK**（`wait_ms=0`，怕卡 UI）。配合 `cleansession=1`，**命令可能静默丢失**。

## 6. 抗连接抖动：业界常用手段（附资料）

先把"抖动"拆成三种形态，**不同形态吃不同的药**：

| 形态 | 表现 | 药 |
|---|---|---|
| 丢 | 少了一段数据 | 序号 + 只认最新（连续量）/ 重传 + ack（离散量） |
| 重 / 乱 | 同一段数据来两次、顺序颠倒 | 序号去重、只接受更新的包 |
| 晚 / 假死 | 连接还在，数据停了 | 心跳 + 新鲜度判定 + 超时降级 |

### 6.1 心跳与新鲜度（deadline / liveliness）

传输层心跳（MQTT `keepAlive`）是**秒级**的，只负责发现"连接死了"。业务层需要自己的**毫秒级新鲜度判定**——数据年龄超过阈值就判为不可信。

工业界的标准实现是 **ROS 2 QoS 的 `deadline` + `liveliness`**：`deadline` 声明"我至少每 X ms 发一次"，`liveliness lease duration` 声明"我多久没说话就算死"，订阅端据此触发回调。这套模型正是我们那条"300 ms 超时 + 变灰"的教科书版本。

- ROS 2 QoS 官方文档：<https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/topics/About-Quality-of-Service-Settings.html>
- 各策略到 DDS 的映射与验证：<https://docs.ros.org/en/humble/p/rmw_int2dds_cpp/qos_mapping.html>

### 6.2 序号 + 去重 + 只认新包

QoS 1 = at-least-once，**重复是协议允许的**（不是 bug）。通行做法：每包带 `seq`，接收端只接受"比上次新"的包，重复包和乱序旧包**不得刷新接收时间**（否则超时判定会被旧包续命，掩盖故障）。

### 6.3 重连：指数退避 + 抖动（jitter）

固定间隔重连在多客户端场景会形成**重连风暴**：20 台客户端同时掉线，又同时重连，把 broker 打崩，然后一起再重连——负载雪崩。

- 经典文章（Marc Brooker, AWS）：*Exponential Backoff And Jitter*，给出 Full / Equal / Decorrelated 三种抖动策略。
- AWS Well-Architected **REL05-BP03 "Control and limit retry calls"**：要求指数退避 + 抖动 + 最大重试次数/预算。 <https://docs.aws.amazon.com/wellarchitected/2022-03-31/framework/rel_mitigate_interaction_failure_limit_retries.html>
- 开源实现参考：`paho.mqtt` 的重连（`reconnect_delay_set`，最小/最大退避）、Rust 的 `rumqttc`（SharkClient 用的就是它）、MQTT.js 的 `reconnectPeriod`、mosquitto 客户端的 `reconnect_delay_cap`。

> 对我们而言，抖动主要防的是**赛场现场多客户端同时重连**，不是单机场景。单机最该做的其实是"退避上限"和"别把 UI 卡住"。

### 6.4 会话、保留消息与遗嘱

- **clean session / session expiry**：MQTT 3.1.1 只有"清/不清"两档；MQTT 5 引入 `Session Expiry Interval`、`Clean Start`，可以精细控制"离线多久内帮我排队"。我们用的是 3.1.1 + `cleansession=1`。
- **retained**：broker 为每个 topic 记住最后一条，新订阅者立刻拿到——适合"重连后不要空白"。
- **LWT（遗嘱）**：客户端异常断开时由 broker 代发一条消息，让下游知道"我死了"——比等心跳超时更快。

参考资料：EMQX 会话与消息过期 <https://www.emqx.io/docs/zh/v5.0/mqtt/mqtt-session-and-message-expiry.html>；HiveMQ MQTT Essentials（持久会话与保留消息）。

### 6.5 数据分级：连续量 vs 离散量

这是整套设计里最省事也最容易被忽略的一条：

| 类型 | 例子 | 传输策略 |
|---|---|---|
| **连续量** | 云台角、血量、经济、位置 | 只发最新值，允许丢，丢了等下一包；**不要为它做重传队列** |
| **离散事件** | 中键标点、发射确认、模式切换生效 | 必须可靠：`command_seq` + 回执 + 超时重发；接收端按 seq 去重 |

我们的对接文档已经在连续量上做对了（"连续状态通信只保留最新包，不得补发积压的历史状态包"），但离散量还差一个 **ack 字段**。

### 6.6 幂等与回执

- 命令带 `command_seq`，接收端记录最近处理过的 seq，重复到达直接丢弃（幂等）。
- 关键命令要回执（ack）：否则无法区分"没发出去 / 发出去了没执行 / 执行了没反馈"。Web 界的参考实现是 Stripe 的 `Idempotency-Key`。

### 6.7 时钟：算新鲜度只用本地单调时钟

不要拿对端时间戳算超时（对端时钟可能没同步、可能回跳）。**收到包时记本机时间**，超时判断全用本机时基——我们的文档写的就是"客户端只在收到新 seq 时更新**本机接收时间**"，这条是对的。

### 6.8 分层降级

失效时不要"什么都不显示"，也不要"假装还活着"：

1. 保留最后值 + **变灰**（数据陈旧但可参考）；
2. 明确标注"失联 / 数据无效"（区分"没数据"和"数据是 0"）；
3. 控制类数据超时后**安全清零**（电控侧策略，建议 200–300 ms）。

### 6.9 测试方法（骨架，待细化）

想验证"抗抖动"，得有办法**主动制造抖动**：

| 注入什么 | 怎么做 | 观察什么 |
|---|---|---|
| 丢包 / 延迟 / 乱序 / 重复 | WSL 里 `tc netem`（`loss` / `delay` / `duplicate` / `reorder`）作用在 3333 上 | UI 是否变灰、多久恢复 |
| 假死（连接在、数据停） | `kill -STOP` 官方客户端 / `iptables DROP` / 拔网线 | 多久发现（当前应 ≈20 s） |
| 高频灌数据 | 用**另一个 ClientId** 的脚本按 50 Hz 发 `CustomByteBlock` | UI 线程延迟、日志 I/O、是否丢帧 |
| 重连风暴 | 多客户端同时断开重连 | broker 是否稳定、重连间隔是否发散 |

行业论文里常用的方法是 **Gilbert-Elliott 突发丢包模型**（模拟无线信道的成串丢包），以及 QoS 0/1/2 的对照测量——例如 IEICE 那篇在树莓派 + 网络模拟器上测 QoS 2 在突发丢包下的重传延迟；Atlantis Press 那篇实测 QoS 0 丢包 0.81%、QoS 1/2 为 0、但延迟从 ~55 ms 涨到 ~300 ms。**结论对我们的启示：QoS 1 换来"不丢"，代价是延迟和重复，所以要靠去重和新鲜度兜住。**

- *Reliable Image Transmission in CPS-based Pub/Sub*（MQTT 丢包与分片重传）：<https://export.arxiv.org/pdf/2506.22875>
- *Performance Evaluation of Bottle Press Machine MQTT Data Acquisition*：<https://www.atlantis-press.com/article/125998326.pdf>

### 8.1 和电控确认（写进对接文档前必须敲定）

1. **传输通道与封装**：0x0310 走**图传发射端 UART（921600）**，不是裁判系统串口；小端、150/300 B 定长、50 Hz 上限、是否需要 CRC（链路已有校验时不重复加）。
2. **到包形态实测**：客户端收到的 `data` 是否以 `0x5A` 开头、前 11 字节就是状态包。有了魔数，链路补齐到 150/300 或前后附加字节都不影响识别，联调时确认一次即可。
3. **布局已定稿（文档 v2）**：11 字节零保留，字段与位分配见电控文档第 5 节；客户端的解析、界面和 300 ms 失联已接线，联调时只需确认到包形态。
4. **上行**：走官方 `KeyboardMouseControl`（键位受限，见 4 节）还是走 `CustomControl` 自由字节（车端对应 0x0309），以及必备的回执字段。
5. **失效语义**：谁负责发"无效"（有效位）vs 谁负责判"超时"（客户端）——文档已定，需要电控确认能实现。
